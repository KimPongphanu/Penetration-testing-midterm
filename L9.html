1. Reverse Engineering คืออะไร และทำไมต้องใช้ใน Pentest

Reverse Engineering (RE) คือกระบวนการ "ถอดประกอบ" และวิเคราะห์ผลิตภัณฑ์ ระบบ หรือซอฟต์แวร์ เพื่อเข้าใจการทำงานภายใน หลักการออกแบบ และฟังก์ชันของมัน — เปรียบเหมือนการแยกชิ้นส่วนจิ๊กซอว์ที่ประกอบเสร็จแล้วเพื่อดูว่ามันถูกสร้างมาได้อย่างไร ใช้กันในหลายวงการ ทั้ง software development, hardware design และ cybersecurity

ในมุมของแฮกเกอร์: เมื่อเข้าใจว่าแอปพลิเคชันทำงานอย่างไร ก็สามารถ ทำให้มันทำงานในแบบที่ผู้ออกแบบไม่ได้ตั้งใจได้ — ซึ่งสำหรับฝั่ง Pentest การทำ RE ระบบ/แอปพลิเคชันเพื่อหาช่องโหว่ที่ซ่อนอยู่คือเครื่องมือสำคัญ ที่ช่วยให้ "แฮกเกอร์ฝ่ายดีคิดเหมือนฝ่ายร้าย" เพื่อหาจุดอ่อนก่อนที่ตัวจริงจะเจอ

เป้าหมาย (Goals) รายละเอียด
Understand system behavior เข้าใจอย่างลึกซึ้งว่าระบบทำงานอย่างไร
Identify vulnerabilities ค้นหาจุดอ่อนที่สามารถถูกใช้โจมตีได้
Develop exploits สร้างเครื่องมือหรือเทคนิคเพื่อโจมตีช่องโหว่ที่พบ
Gain unauthorized access ได้สิทธิ์เข้าถึงระบบ/เครือข่ายโดยไม่ได้รับอนุญาต (ในบริบท lab/test)

บทบาทของ RE ในงาน Pentest (3 ด้าน):

  • Identifying Vulnerabilities: ค้นหาช่องโหว่ที่ "มองไม่เห็นด้วยตาเปล่า" จากการถอดรหัสพฤติกรรมซอฟต์แวร์ที่ซับซ้อน
  • Developing Customized Security Solutions: เข้าใจระบบลึกขึ้น → ป้องกันได้ตรงจุดขึ้น ปรับแต่งเฉพาะระบบนั้น
  • Enhancing Cyber Defence Strategies: คาดการณ์แนวทางโจมตีล่วงหน้า → เสริมเกราะเชิงรุก (proactive) ไม่ใช่ตั้งรับอย่างเดียว

2. เทคนิค 5 หลัก · ความท้าทาย · จริยธรรม

เทคนิค ทำอะไร จุดสังเกต
Disassembly แตก compiled code กลับเป็น Assembly language เพื่อดูตรรกะและหาช่องโหว่ ได้ "ภาษาเครื่อง" ที่คนอ่านพอเข้าใจได้
Decompilation แปลง compiled code กลับเป็นภาษาโปรแกรมระดับสูง (อ่านง่ายกว่า Assembly มาก) ใช้ใน Ghidra, Jad (Java)
Static analysis ตรวจโค้ดโดยไม่รันมันเลย เพื่อหาช่องโหว่ที่อาจเป็นไปได้ ปลอดภัยกว่า — โปรแกรมไม่ทำงานจริง
Dynamic analysis รันโค้ดจริงและเฝ้าติดตามพฤติกรรมเพื่อหาช่องโหว่ เห็นผลจริงของโปรแกรม (เช่น ltrace/strace)
Fuzzing ยิง input แปลกๆ / ไม่คาดคิด เพื่อทำให้ระบบพังแล้วหาช่องโหว่ มักใช้คู่กับ dynamic analysis
ความท้าทาย (Challenges) รายละเอียด
Complexity ระบบสมัยใหม่ซับซ้อนมาก จนเข้าใจการทำงานภายในได้ยาก
Obfuscation ระบบอาจถูกทำให้อ่านยากโดยเจตนา (เช่น code ที่ถูกอำพราง)
Legal implications การ RE อาจติดประเด็นกฎหมาย โดยเฉพาะซอฟต์แวร์กรรมสิทธิ์ (proprietary software)
ข้อพิจารณาด้านจริยธรรมและกฎหมาย (สำคัญมาก):
  • Obtain authorization: ต้องมีสิทธิ์/ความยินยอมก่อนทำ RE เสมอ — การเข้าถึงหรือวิเคราะห์โดยไม่ได้รับอนุญาตอาจมีโทษทางอาญา
  • Respect intellectual property: ระวังลิขสิทธิ์/สิทธิบัตรของเป้าหมาย — RE ต้องทำเพื่อวัตถุประสงค์ที่ชอบธรรม
  • Use tools responsibly: ใช้เพื่อ security testing, vulnerability research หรือการเรียนรู้เท่านั้น
  • Respect privacy: ระวังข้อมูลส่วนบุคคล — จัดการข้อมูลอ่อนไหวด้วยความรอบคอบตามนโยบายความเป็นส่วนตัว

4. คำสั่งพื้นฐานบน Kali — File Inspection & Analysis

4.1 File Inspection — รู้จักไฟล์ก่อนอื่น

คำสั่ง ทำอะไร / ตัวอย่าง
file บอกชนิดของไฟล์ — ขั้นแรกที่ขาดไม่ได้ เพราะต้องรู้ก่อนว่าเจอ text, binary executable, script หรือ image
file mysterious_file
strings ดึงข้อความที่อ่านได้ (printable strings) จากไฟล์ binary — ใช้หา error message, URL หรือแม้แต่ flag ที่ฝังอยู่ในโปรแกรม
strings my_program
hexdump -C / xxd แสดงไฟล์ในรูปแบบ hexadecimal ดิบ — ดู byte pattern ที่ไม่ปรากฏเป็นข้อความ
hexdump -C my_file

4.2 File Analysis — ดูพฤติกรรมและคำสั่งจริง

คำสั่ง ทำอะไร / ตัวอย่าง
ltrace ติดตามlibrary calls — โปรแกรมเรียกใช้ฟังก์ชันจาก shared library อะไรบ้าง (เช่น เปิด network หรือเขียนไฟล์) ช่วยเดาจุดประสงค์ของโปรแกรม
ltrace ./my_program · กรองเฉพาะฟังก์ชัน: ltrace ./crackme4 strcmp
strace ติดตามsystem calls — เห็นโปรแกรมคุยกับ OS ระดับล่าง เช่น open, read, write, socket, connect
strace ./my_program
gdb GNU Debugger — รันโปรแกรมทีละบรรทัด ตั้ง breakpoints และตรวจสอบหน่วยความจำ เป็นเครื่องมือพื้นฐานที่สุดในการทำความเข้าใจ flow การทำงาน
gdb ./my_program
objdump -d แสดงข้อมูลจาก object file รวมถึง disassembly ของ executable — อ่าน assembly code เพื่อดูคำสั่งดิบของโปรแกรม
objdump -d ./my_program
เกร็ด: ltrace = ระดับ "ฟังก์ชัน/library" · strace = ระดับ "ระบบปฏิบัติการ" — ถ้าโปรแกรมอ่านรหัสผ่านแล้วเทียบด้วย strcmp ให้ใช้ ltrace แต่ถ้าต้องรู้ว่าโปรแกรมเปิดไฟล์/ต่อเน็ตที่ไหน ให้ใช้ strace

5. Workflow วิเคราะห์ Binary ทีละขั้น

สมมติมีไฟล์ binary ชื่อ challenge — ลำดับที่สไลด์แนะนำ:

  1. ระบุชนิดไฟล์: file challenge
  2. ดึงข้อความที่อ่านได้: strings challenge | less (pipe ไป less เพื่อเลื่อนดู output ยาวๆ) — มองหาอะไรที่น่าสนใจ เช่น hint หรือ flag
  3. รันพร้อมติดตามพฤติกรรม: strace ./challenge หรือ ltrace ./challenge → สังเกตการทำงาน
  4. Disassemble: objdump -d ./challenge | less → ได้ assembly code ไว้วิเคราะห์ตรรกะของโปรแกรม (เช่น การเช็ครหัสผ่าน)
ELF (Executable and Linkable Format): ไฟล์ฟอร์แมตมาตรฐานบนระบบ Unix-like (Linux, FreeBSD, Android) สำหรับ executable files, object code, shared libraries และ core dumps — ให้โครงสร้างที่ยืดหยุ่นและขยายได้สำหรับเก็บ binary code และ data ที่ OS ต้องใช้รันโปรแกรม (คู่กับ PE บน Windows)

6. Assembly Code Analysis — หารหัสผ่านจาก objdump

เป้าหมายหลัก: หาจุดรับ inputและจุดตัดสินใจ (decision point) ภายในโปรแกรม เพื่อวิเคราะห์ตรรกะการตรวจรหัสผ่าน

ขั้น มองหาอะไรใน assembly
1. หาจุดเริ่มต้น (Main Function) โปรแกรมส่วนใหญ่เริ่มที่ main — จุดที่รับ input จากผู้ใช้และตรวจ credential
2. หาฟังก์ชันรับ input ค้นหาการเรียกฟังก์ชันมาตรฐาน เช่น scanf, fgets, gets
3. หาจุดตัดสินใจ (Comparison Logic) คำสั่งเปรียบเทียบ: cmp (Compare) และ test ตามด้วย conditional jumps:
je (Jump if Equal) — กระโดดเมื่อค่าตรงกัน = รหัสผ่านถูก
jne (Jump if Not Equal) — กระโดดเมื่อไม่ตรง = รหัสผ่านผิด
4. หา Hardcoded Credentials ค่าที่อยู่ติดกับคำสั่ง cmp หรือค่าที่โหลดเข้า register ก่อนเทียบ มักเป็นรหัสผ่านจริง

ตัวอย่างจริง (Task 6 — crackme6): objdump เผยชุดคำสั่งเทียบทีละตัวอักษร:

cmp $0x31,%al · cmp $0x33,%al · cmp $0x33,%al · cmp $0x37,%al · cmp $0x5f,%al · cmp $0x70,%al · cmp $0x77,%al · cmp $0x64,%al

นำค่า hex มาต่อกันได้ 313333375f707764 แล้วแปลงจาก hex เป็นข้อความ:
echo "313333375f707764" | xxd -r -p → ได้รหัสผ่าน 1337_pwd

เกร็ดการอ่าน hex: แต่ละคู่ 0x31 0x33 … คือ ASCII หนึ่งตัว (0x31 = '1', 0x5f = '_', 0x64 = 'd') — การอ่าน cmp ทีละตัวแบบนี้คือหัวใจของการ crack binary พื้นฐาน
